# v0.7.2-dev.2 — observation history and evaluation

This preview preserves dev.1 geometry thresholds. It adds bounded observation history for every source, selected trails, analytical JSON download, offline motion replay, geometry gate diagnostics, and observed-descent arrival scenarios.

## Local history and export

Select an aircraft marker. With **Selected trail** checked, the map draws the last retained hour in cyan. Active geometry support is highlighted in magenta with start/end markers. Uncheck to hide. Selection does not change the motion filters or force map fitting. Trails refresh every ten seconds, break at recorded gaps/discontinuities/occurrence changes, and split at the antimeridian. The selected trail remains available after a marker leaves the current feed, until its samples expire.

Use **Export selected** or **Export hour**. History is transient: a restart clears it. Tracks that leave the feed are retained for the remainder of their one-hour sample window. Limits are 1,024 tracks and 360 observations per track, at least ten seconds apart. This is sampled history, not every incoming message; TFMS/flights.js remain coarse and excluded from motion classification even though their observed positions can be drawn/exported.

Relative to the map's URL:

- `aircraft-history?hex=a248f9` — retained tracks matching the six-digit ICAO (including reported SFDPS ICAO).
- `aircraft-history?track_id=~localid` — exact source-local identifier, as shown in the popup. URL-encode the value.
- Add `&download=1` to download JSON.
- `aircraft-history?download=1` — explicitly download all retained tracks.
- Up to 32 comma-separated exact identifiers can be selected with `track_id` (legacy internal `keys` selector is also accepted). A hex can match multiple retained source-local occurrences; all matches are returned, subject to the selection limit.

Unknown hex returns 404. Invalid selectors or unselected interactive requests return 400. JSON is schema version 1, recording source, build version, generation time, sampling limits, track identity, samples, source/receipt timestamp provenance, altitude, reported speed/course/vertical rate, position-derived leg speed, field metadata, segment boundaries, and sampled motion state/evidence when available. Top-level `motion` provides current/completed retained motion events. JSON timestamps are Unix seconds in UTC. Null means unavailable, not zero.

The recorded `motion` on a sample is the latest engine analysis at collection time; analysis can lag a sample by its configured cadence. Derived speed is omitted across segment breaks. Missing report time excludes SFDPS observations. No interpolation or synthetic landing is inserted. Last observation is not proof of touchdown, gate arrival, or track termination. Enrichment identity/type may be absent; exports are not complete airline itineraries. Touchdown predictions themselves are not recorded as a time series in this preview.

## Offline replay

From the source directory:

```sh
python tools/replay_aircraft_history.py recording.json -o replay.json
```

The replay uses the source profile and feeds exported samples in time order, preserving recorded segment boundaries. It recalculates motion from the sampled data; this may differ from live classification because live motion also used intervening samples omitted by the ten-second export cadence. It does not replay the browser touchdown model or automatically label touchdown outcomes. Exported observations provide inputs for subsequent ETA evaluation work. Keep captured recordings out of the public source repository; tests use synthetic data.

## Observed descent and estimated touchdown

The existing transport-jet, freshness, inbound, turn, orbit and altitude gates remain. A supported `descending` primitive with at least 30 seconds of support and a fitted vertical rate at or below -300 ft/min selects observed-descent mode immediately, regardless of destination distance. Brief fluctuations leave the previous cruise-then-descent scenarios intact.

Above 10,000 ft above airport elevation, the measured descent magnitude is clamped to 500–3,000 ft/min; faster/slower scenarios use multipliers 1.2/0.8. The early-descent duration is bounded by the existing profile descent duration and the distance available after reserving terminal descent distance. Speed changes linearly from current reported ground speed to the existing 250/230 kt endpoints. The existing 10,000–3,000 ft and final descent stages remain unchanged. If the early descent finishes before the destination, remaining distance is an explicit **arrival level-off allowance** at the early-stage endpoint speed, not additional high-altitude cruise. This is an assumed scenario, not a forecast of an ATC clearance or observed future level-off. Below 10,000 ft the existing terminal phases apply and any excess distance likewise receives a level-off allowance. If the descent profile requires more than the available direct distance, the estimate remains unavailable. Popup assumptions identify the selected stage.

The model does not extrapolate measured deceleration to zero speed or assume an airport-specific 200–300 NM trigger. Validate actual touchdown, separately from gate estimates. ±15 minutes remains an evaluation target, not a demonstrated accuracy claim.

## Geometry diagnostics

Verbose summaries include `geometry_gate_rejections`: sums from the latest geometric analysis of retained tracks. Counts refer to overlapping candidate windows, not unique aircraft or a since-last-summary delta. Gates identify insufficient history, unusable chord speed/time, short phases/straights, turn angles/directions, nonreciprocal/unequal straights, circle-fit rejection, unequal radii, migrating centers, closure and corridor exits. Circle rejection groups singular fits, radius limits, and excessive residual; it does not claim which subcheck failed.

`pattern_transitions_total` counts candidate starts, established starts and ends since engine startup. A candidate becoming established ends one state and starts the next. Completed events retain their end reason. The verbose popup also lists current gate names. No per-aircraft identities are added to periodic logs.

## Network and FAA behavior

Direct HTTP GET/POST requests require the socket peer to match `trusted_networks`, a comma-separated CIDR list. Defaults: loopback, RFC1918 private IPv4, and IPv6 ULA. Narrow this to your actual trusted subnets if appropriate; retain the HA Ingress proxy's subnet if using Ingress. Forwarded-address headers do not grant access. The optional host port remains unpublished by default.

This is a peer allowlist, not authentication. A reverse proxy/NAT can hide the original remote client. Home Assistant authenticates its Ingress users; protect direct LAN exposure with network controls. This application does not modify host firewall rules. A changed allowlist requires restart, so an incorrect list may deny Ingress until corrected through app configuration.

Analytical trails/downloads include SFDPS and TFMS observations for personal retention and non-operational analysis. This is distinct from automatic bridging: FAA dump1090/aircraft.json, external track-history proxy, and generic live motion/feed outputs remain disabled. Existing FAA density export/range restrictions are unchanged. The analytical endpoint is request-driven, not a configured outgoing feed.

This product boundary is not a claim that FAA terms prohibit every export. The supplied SAA v1.0 discusses internal distribution (p.3), and SCDS Guidelines v1.1 §3.4.2 discusses development/test/internal redistribution. Users must apply relevant service-specific terms and historical LADD protections. No LADD list loader/filter is implemented by this increment, and upstream filtering is not asserted to cover subscriber-level blocks. Publishing source code does not publish captured observations. No FAA documents, credentials or real captured tracks are bundled with this build.
