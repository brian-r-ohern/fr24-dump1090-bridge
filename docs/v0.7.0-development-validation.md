# v0.7.0-dev.4 — Larger aircraft and local SFDPS view

This development build follows dev.3. The first public motion release remains v0.7.0.

## Aircraft markers

Aircraft SVG display size increases from 24 × 24 to 36 × 36 screen pixels (1.5× each dimension). Leaflet marker size is also 36 × 36 and its anchor changes from 12,12 to 18,18. The SVG viewBox remains 24 × 24; changing the viewBox would alter the artwork rather than its display size. Motion colors, military styling, closest glow and O/D badges remain available. Home icons are unchanged.

## Configure SFDPS

1. Select `source: swim_sfdps` in App Configuration.
2. Enter the FAA-authorized **SFDPS** Solace broker host, message VPN, subscription username/password and durable queue/JMS name in the existing `swim_*` fields. A TFMS queue is not an SFDPS queue.
3. Save and restart the App. The input source selects the parser/product automatically; the legacy `swim_product` field cannot override it.
4. Home Assistant Home must be available. Until then, messages are counted but no aircraft positions are retained. `swim_radius_nm` applies to observed positions, with the existing 250 NM default.
5. Open the Web UI. Its title/card identifies **FAA SFDPS · local view**. Full four-letter airport identifiers match native route O/D codes, e.g. `KSYR`.

SFDPS is a mutually exclusive local-view source. No SFDPS density store is opened or migrated; collection, backups/imports, GeoJSON, density envelopes and motion analysis are disabled. Existing ADS-B/TFMS density and ADS-B range files are preserved. Switch back to the corresponding source to use its history. SFDPS does not gain destination ETA modeling in this increment.

## FAA isolation

`/aircraft.json` and `/data/aircraft.json` return **403** for **both TFMS and SFDPS**, including requests carrying `client_id`. The existing code previously served TFMS there; dev.4 closes that output. Track-history proxy and density JSON/GeoJSON exports/envelope APIs also reject FAA-source requests. Range processing and exports remain disabled for FAA sources. ADS-B source endpoints are unchanged.

The local map refreshes its own HTML document every five seconds and consumes escaped, in-memory display state embedded in that document. It does not use a separate FAA aircraft feed endpoint. TFMS density likewise refreshes bounded recent display geometry through that HTML view; its generic density JSON/GeoJSON endpoints are closed. Local visualization necessarily delivers display information to the viewer's browser; this is not an authorization mechanism, and the direct LAN Web UI remains unauthenticated. Keep it local. Do not publish FAA captures, display state or derived datasets. No captured FAA data is bundled in this release or its test fixtures.

TFMS retains its existing local density collection/view; SFDPS has no density in dev.4. The dashboard integration consumes status counters, not FAA aircraft records. External ADSB Tracker enrichment/history lookup is disabled for FAA views; their native route metadata remains visible.

## Parser and continuity contract

The first adapter supports the FIXM 3.x MessageCollection/flight structure in the supplied SFDPS capture. Namespace prefixes are irrelevant; field scope is explicit:

| Meaning | Field / rule |
| --- | --- |
| Observed position | `flight/enRoute/position/position/location/pos`, EPSG:4326, latitude then longitude |
| Observation time | Parent `position/@positionTime`, timezone-qualified |
| Evidence | Parent `position/@reportSource = SURVEILLANCE` |
| Observed altitude | Direct child `altitude`, `uom=FEET`; never assigned/target altitude |
| Reported speed | `actualSpeed/surveillance`, `uom=KNOTS`; displayed as reported speed |
| Flight occurrence | `gufi`; a callsign alone is insufficient |
| Callsign | `flightIdentification/@aircraftIdentification` |
| Native route | `departure/@departurePoint`, `arrival/@arrivalPoint` |
| Optional reported ICAO | Supplemental `ADSB_02M_52B`, only a valid six-digit hexadecimal value |
| Course | Derived from successive observed positions/timestamps; no unverified velocity-axis conversion |

`targetPosition`, `targetAltitude`, route waypoints and assigned altitude never substitute for an observed position/altitude. Non-surveillance reports, unsupported CRS, invalid coordinates, missing GUFI, unqualified time and malformed XML are rejected or omitted as appropriate. Unrecognized altitude/speed units are omitted. The reported altitude reference and reported-speed semantics are not promoted into validated ADS-B motion inputs.

SFDPS position times more than `swim_aircraft_timeout` seconds old or more than five seconds in the future are excluded at admission. Equal/older position updates do not replace a newer track or extend its receipt timeout. Aircraft expire after the configured receipt timeout; the in-memory view is capped at 4,096 flight occurrences, evicting the least recently accepted track at capacity. Source-local hashed GUFI identifiers are distinct from actual ICAO addresses. Private GUFIs are not inserted into browser display state, diagnostics or logs.

The shared course estimator needs distinct time-ordered positions, no more than 300 seconds apart, at least 0.05 NM displacement and implied speed no greater than 1,200 kt. A stationary update may retain the previous course. This is a map orientation estimate, not the motion-analysis engine.

No missing position/time, unsupported CRS or non-surveillance reports occurred in that capture. This validates that sample's structure; live broker connectivity, ACK behavior, AppArmor and browser presentation still require the user's HAOS test.

Synthetic tests cover scoped observed fields, unknown units, invalid time/coordinates, missing GUFI, namespace changes, malformed XML, settings recovery, geography/Home gating, stale/future/duplicate updates, calculated course, blocked feeds/exports, disabled persistence/collection, escaped HTML display state and marker dimensions. Live checks: larger icons centered while turning; native O/D and route metadata; first update may have unknown course, second moving update gains course; source/product/status counters; no Density/range/motion controls; FAA feed URLs return 403; switching back to SBS recovers its normal feed and existing history. ## Enable diagnostics

In App Configuration enable **Verbose diagnostic logging** (`verbose_logging: true`), save, and restart the App. Existing installations default to false; explicitly enable it for this test and leave it enabled for the next geometry increment. Settings backup/recovery retains the toggle. Turning it off restores the existing normal log volume; cumulative reason counters remain available in `/status` and `/motion/status`.

Motion diagnostics appear at most once per minute beside the ordinary Motion summary. They include interval counter deltas, cumulative rejection reasons, retained samples/events, and latest batch time. Fixed categories: missing coordinates, invalid coordinate values (including non-finite/non-numeric values), out-of-range coordinates, nonpositive selected position time, and future selected position time. Reasons sum to `invalid`; duplicates, throttled updates, gaps, out-of-order observations, and discontinuities stay separate. Missing coordinates are often expected for partially populated SBS aircraft. Counts represent snapshot attempts, not distinct aircraft or malformed SBS messages. Malformed optional timestamp metadata still follows existing fallback rules; it is not newly rejected. First verbose delta covers activity since startup (or since the prior verbose summary), not necessarily exactly one minute.

Density diagnostics break down lock wait, database preparation, SQLite execute/fetch, Python aggregation, display aggregation and GeoJSON geometry creation. SQLite time includes database work, I/O and scheduling; it is not a measurement of disk time alone. `aggregated_rows_read` counts grouped SQL results, not scanned underlying observations. Monthly timing entries identify which retained chunk consumed time, without logging coordinates. Geometry time is separate from `query_seconds`; `geojson_seconds` includes query and geometry. HTTP serialization/network/browser rendering are outside those timers. Cached queries may have zero SQL time.

## Collect evidence

Refresh density at the same viewport and band selection three times, waiting at least 31 seconds between requests to avoid the Bridge cache. Capture Density diagnostics and Density geometry lines. Alternatively a bounded ADS-B diagnostic request such as `/traffic-density.geojson?zoom=11&max_cells=6000&bypass_cache=1` forces recomputation; keep the same bbox/date window when comparing viewport requests. `bypass_cache=0` retains normal caching. This option does not erase stored data or clear SQLite/filesystem caches.

Each uncached monthly query includes:

- `query_plan`: SQLite EXPLAIN QUERY PLAN details, bounded to 32 entries of 300 characters, without bound coordinate/date values. Look for table scan versus index search, join order and temporary GROUP BY B-trees. A scan can be appropriate for a broad viewport; do not assume every scan is a defect.
- `database`: SQLite version, page_count/page_size, cache_size (negative values are KiB), temp_store (0 default, 1 file, 2 memory) and journal mode. These values are read-only; the build does not change pragmas or run ANALYZE.
- `vm_steps_approx`: progress callbacks every 10,000 virtual-machine instructions multiplied by 10,000. This is approximate work, not a row count; values below 10,000 may report zero. Instrumentation introduces some overhead. The callback is removed even when query execution fails.
- `execution_thread_cpu_seconds`: CPU used by the executing thread during SQL/fetch and Python row aggregation. Compare against SQL wall time with care: the CPU timer includes row aggregation, does not identify disk time, and excludes other threads.

Cached requests do not execute SQL, so have no monthly plan entry. Existing phase timers remain. `aggregated_rows_read` is grouped output, not scanned input records. This build deliberately avoids extra full COUNT queries that would add another expensive read.

All supplied dev.5 invalid counts were missing coordinates. The legacy counter is preserved; use rejection_reasons to distinguish ordinary unpositioned aircraft from invalid coordinate/time values. No motion thresholds or admission rules change here.

# v0.7.0-dev.7 — Viewport density SQL optimization

This development build changes query execution, not collected measurements. Fine zoom-17 history, monthly files, 18-month retention, altitude/passage counters, import/export formats, and actual observed-cell semantics remain unchanged. No new index, database migration, cache-size increase, ANALYZE or schema rewrite occurs.

## Query strategy

Viewport requests (`bbox`) use `viewport_first_numeric`: search existing `cell_locations_xy` for candidate cells, then read each cell's daily records using the existing `(cell,day)` primary-key index. SQLite CROSS JOIN prevents reversal to the date-first plan observed in dev.6. GROUP BY uses numeric x/y coordinates shifted to the requested parent zoom, replacing repeated parsing of text cell IDs. Parent-cell viewport edge inclusion and the existing exact polygon intersection check remain unchanged.

Requests without a viewport use `date_first_numeric` and retain date-first planning for whole-window exports. Dates and altitude selection are unchanged. An x/y index uses the x range then tests y; it is not a true two-dimensional R-tree. Wide viewports still require real aggregation work and may remain slow.

Expected viewport plan in verbose Density diagnostics:

```
SEARCH l USING INDEX cell_locations_xy (x>? AND x<?)
SEARCH d USING INDEX sqlite_autoindex_daily_1 (cell=? AND day>? AND day<?)
USE TEMP B-TREE FOR GROUP BY
```

The temporary grouping B-tree may remain; its presence alone is not an error. The shared collection/query lock remains in this increment. Reducing query work should reduce time holding it, but lock wait has not been eliminated. Approximate VM instructions and phase timers remain enabled only as documented in dev.6. Instruction counts are not underlying-row counts.

Official SQLite join-order behavior: https://www.sqlite.org/optoverview.html#manual_control_of_query_plans_using_cross_join

# v0.7.0-dev.8 — Parent-day aggregates and density tiles

This development build targets broad-view density refreshes. Fine zoom-17 observations remain authoritative. No position interpolation, synthetic observations, permanent coarsening or change to altitude/passage semantics is introduced.

## Map controls

- **Load density** loads the current viewport and selected altitude bands, reusing valid density tiles. Enable the layer to load its first view. Pan/zoom/band changes remain manual; the map prompts to load density again.
- **Refresh now** bypasses cached tiles for the visible view and recomputes them from stored observations. Both buttons are disabled while their active request runs.
- **As of** shows the oldest tile generation time in a composite view. Tiles can be up to two hours old while collection continues. An empty cached tile can remain empty until expiry or Refresh now; the collector still records new observations.
- Map tiles here are geographic quadtree batches of observed-cell GeoJSON, not rendered PNG basemap tiles. Colors and polygons retain the existing display rules. The render limit still aggregates observed children to parents when necessary.

## Persistent parent-day totals

Monthly `.dat` SQLite chunks gain derived tables for zooms 8, 11 and 14. A requested zoom through 14 uses the nearest stored parent level at or above it; zooms 15–17 retain fine-cell queries. These totals hold all altitude counters, summed base-cell passage counts, altitude extrema, timestamps and history-completeness flags.

The first request for a level/day performs an atomic, resumable backfill from fine records. `[INFO] Density parent rebuild started/completed` identifies month, level, day count and elapsed time. Empty days get readiness markers but no observation records. Ready-day checks read at most a month's readiness records instead of rescanning fine history.

After backfill, SQLite triggers update parent totals in the same transaction as ordinary observation collection. Deletion or replacement that cannot be represented as a monotonic observation marks affected days dirty; the next query rebuilds those days. Restore remains a deterministic whole-cell/month operation. Clear deletes fine data and derived totals/readiness. Retention deletes entire expired chunks. Derived records do not enter JSON backups or become another source of observations.

Parent totals persist across normal restart/upgrade and increase database storage. Existing metadata/schema version and fine-record formats stay compatible; older builds can still read the base records, though derived triggers remain in the chunk. A fine JSON restore rebuilds parents lazily. No data is discarded. First backfill and dirty-day rebuilding use the existing collection/query lock and can temporarily delay publication/collection; let the first request finish. Warm views avoid repeating that work.

## Two-hour tile cache

The map uses `/traffic-density/view` for ADS-B sources. Tiles are keyed by source, inclusive UTC date window, altitude selection, requested density zoom and geographic tile coordinates. They expire after 7,200 seconds. Cache hits require no SQL. Clear, restore and retention pruning invalidate them immediately. Full export routes continue to read stored data, without the tile cache.

Caches are in memory and deliberately do not survive App restart. Persistent parent totals make rebuilding cheap. Each store keeps at most 128 entries and 32 MiB of serialized cell records; actual Python object overhead is additional. A tile is normally 32 × 32 requested-grid cells. Requests needing over 64 tiles, or lacking a bbox, fall back to the bounded conventional view and report an uncached generation time. No extra permanent tile files are created.

`/traffic-density/status` reports cache entries, serialized bytes, TTL and limits. Verbose `[DEBUG] Density tile view` reports hits/misses, requested/display/tile zooms, timing and underlying monthly plans on cache misses. Cached views have no monthly SQL plan. `bypass_cache=1` forces fresh visible tiles. Tile cache generation time describes the computed density view, not aircraft position freshness.
