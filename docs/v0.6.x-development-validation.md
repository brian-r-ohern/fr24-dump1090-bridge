# v0.6.3 — source identity, density archives and range controls

> Historical development note for the version named above. Later iterations supersede some limits and UI behavior. See the [current App guide](https://github.com/brian-r-ohern/fr24-dump1090-bridge/blob/main/fr24-dump1090/README.md) and [changelog](https://github.com/brian-r-ohern/fr24-dump1090-bridge/blob/main/fr24-dump1090/CHANGELOG.md) for v0.6.8 behavior.

## Upgrade and retain your existing density

The source grid stays at geographic quadtree zoom 17; existing monthly counters
and provenance are retained. Source-specific files now live under
`/data/traffic-density/<source>/YYYY-MM.dat`.

Old versions did not record which feed collected their history. For your SBS
instance, add this App Configuration option when upgrading, then restart:

```yaml
density_legacy_source: sbs_30003
```

Use `swim_tfms`, `flights_js` or `aircraft_json` only when that source actually
collected the old history. If it contains a mixture, keep the original export
and identify/reconcile it before assigning it to a single feed. Never assign a
mixed history merely because a source is currently selected.

When old monthly files exist and this option is unassigned, the Bridge still
runs but density collection pauses with an explanation on the status page.
Migration moves the existing files without adding, rewriting counters or
changing the collector provenance. An interrupted move resumes on restart.
Old history can be attributed to one source while a different source is active;
the selected source then gets its own empty dataset. Changing the selected
source later reopens that source's retained history. New installations need no
legacy setting.

## Titles and Home Assistant sidebar

Browser document titles, status-page headings and map headings automatically
follow the selected source:

| Configuration source | Page/map title | Export prefix | Suggested sidebar title |
| --- | --- | --- | --- |
| `sbs_30003` | SBS → dump1090 | `sbs-` | Bridge SBS |
| `flights_js` | FR24 HTTP → dump1090 | `fr24-` | Bridge FR24 HTTP |
| `aircraft_json` | ADSB JSON → dump1090 | `d1090-` | Bridge dump1090 |
| `swim_tfms` | FAA TFMS → dump1090 | `faa-` | Bridge FAA TFMS |

The App's default sidebar entry is **Bridge**. Home Assistant reads its ingress
sidebar label from the static `panel_title` in `config.yaml`; the runtime source
setting cannot change that label. To distinguish your local and GitHub
installations in the sidebar, use `panel_title: "Bridge SBS"` in the local
installation's manifest and `panel_title: "Bridge FAA TFMS"` in a GitHub fork's
manifest, then refresh/reinstall the corresponding App metadata as needed.
Keep the existing slug and each installation's repository identity to retain
its data. Do not uninstall an instance just to change its label. A GitHub fork
with its own manifest retains the label across upstream updates if that change
is kept. This release does not install additional App copies or alter Supervisor
metadata at runtime.

## Density and range behavior

All four sources continue collecting density whether the map or layer is open
or closed. The map's Traffic Density checkbox starts off. Altitude band counts
remain in storage/API; selectable altitude heat maps are still a follow-on.

**Range ring** starts checked for the three ADS-B sources. Unchecking it removes
the outline without stopping range collection. FAA TFMS neither starts the
range worker nor loads or modifies range files, offers no range-ring control,
and rejects range backup/import routes. Existing range history is preserved.
Range coverage remains the existing independent App-level dataset for ADS-B
modes; this release splits density by source, not historical range files.

## Backup/restore and large files

The status page and density endpoints expose only the current source. Examples:

- `sbs-traffic-density.json`
- `sbs-traffic-density-2026-10.json`
- `sbs-traffic-density.geojson`
- `sbs-range-coverage.json`
- `faa-traffic-density.json` (FAA has no range backup)

New JSON density backups contain `source_type`; an import for a different source
is rejected. Filenames do not determine import identity. For an older untagged
backup, explicitly check **This older, untagged backup belongs to [current
source]** before restoring. API clients may provide
`?legacy_source=sbs_30003` (or the matching current source) as the equivalent
explicit attribution. The whole cell/month winner policy remains deterministic;
overlapping histories are never summed and uncertain starts stay null.

Full JSON and GeoJSON downloads are compact and disk-staged from consistent
SQLite snapshots. Uploads use the browser File directly rather than converting
it to a giant JavaScript string. The server decodes and validates one monthly
cell record at a time into temporary SQLite staging, validates the entire
archive and its source before touching live data, and then restores by monthly
transaction. The previous 256 MiB import ceiling is removed. Reads and transfers
use 64 KiB chunks; a single cell/month JSON record is limited to 1 MiB, well
above the normal 31-day record size. Monthly restore transactions still commit
independently if an I/O failure occurs while applying an already valid archive.

Temporary files are automatically removed after completion, failure or a client
disconnect. They reside in the current source directory. Allow additional free
space for a snapshot of the selected SQLite history plus the generated export,
or the compact staging database during import. A process killed mid-operation
can leave a `.export-*` or `.restore-*` working directory, which can be removed
while the App is stopped. The status endpoint's `bytes_on_disk` reports monthly
SQLite storage, not pretty-printed backup size or these temporary files. Compact
JSON changes whitespace only and may be substantially smaller than prior
indented exports; GeoJSON is generated on request, not retained as another dataset.

Map requests with a bounding box keep the existing recent-window response path.
Large whole-area GeoJSON exports use disk staging. The snapshot copy and the
application phase of a restore briefly hold the collector lock; export
serialization/download and upload validation do not hold it. On very large
histories the copy/restore phase can delay density updates. SQLite files retain
18 calendar months; dividing them by source does not reduce per-source growth.

## Upgrade

## Altitude heat maps

Enable Traffic Density, then expand Altitude selection. All Traffic is initially
selected and includes Unknown. Low, Middle and High can be combined. Checking
an individual band clears All Traffic; checking All Traffic clears the bands.
Unchecking every selection displays no cells and prompts for altitude bands.

Color normalization uses the maximum selected observation count in the visible
response. Different selections/zoom levels can have different color scales;
compare counts rather than treating a color as one fixed numeric density.
Popups show selected observations plus all-band statistics for context. Passage
counts and history/altitude extrema remain the stored all-band cell statistics.
Filtering does not change collection, retention, full JSON backups or imports.
Cells with zero selected observations are omitted from a filtered view.

`/traffic-density` and `/traffic-density.geojson` accept `bands=all` (default),
`bands=low`, `bands=middle`, `bands=high`, combinations such as `bands=low,high`,
and `bands=none`. Unknown is available through All Traffic. Invalid selections
are rejected. Existing `start`, `end`, `zoom` and `bbox` parameters remain.
Responses retain the complete per-cell counters and add
`selected_observation_count`; window metadata records `selected_bands`.
Full `/traffic-density/export` backups always contain all stored counters.

## Density-derived envelopes

For ADS-B sources, expand Density envelopes · comparison and click Generate /
refresh. Initial comparison toggles select Low, Middle and High; All is optional.
These dashed outlines are independent of the authoritative red Range ring and
of the density heat-map checkbox. Generation is explicit, not a periodic whole
history scan. The map uses the same default recent 30 UTC dates as heat maps.
The status page supports arbitrary inclusive UTC start/end dates and exports.

- `/traffic-density/envelopes?start=2026-10-01&end=2026-10-06`
- `/traffic-density/envelopes.geojson?start=2026-10-01&end=2026-10-06`

Omitting dates selects today and the 29 preceding UTC dates. All four products
are calculated together from the same source snapshot, dates and Home position.
The outputs use **0.5° / 720 bins**, with the same nearest-sector-center bearing
assignment as existing range coverage. Missing sectors stay missing: drawn runs
break at every gap, including across north. No unsupported connection closes an
incomplete envelope. Export polygons are not used; GeoJSON provides stepped
LineStrings plus maximum-support cell-center Points and their sector statistics.

The status page downloads use `sbs-`, `fr24-`, `d1090-`, or `faa-` prefixes,
for example `sbs-density-envelopes.json`. Every result identifies its source,
UTC window, Home position, generation time, cache status and non-authoritative
purpose. The existing 0.5-degree range dataset remains untouched and authoritative;
this release does not compare against or consolidate the old 1-degree baseline.
Existing legacy backup/migration compatibility remains available.

The cache keeps at most four source-store/window/Home combinations per running
store and expires after five minutes. Source-store changes, Home/date changes,
UTC-day changes and successful restores prevent reuse of an inappropriate result.
New live observations can take up to five minutes to appear in a regenerated
comparison. Cached data never enters persistent density/range storage.

## Interpretation and evidence limits

Density stores observed cells, not original positions within them. Ranges and
bearings therefore use base-cell centers; the approximation is roughly bounded
by the distance from a center to its cell boundary and depends on latitude.
Small angular errors are possible, particularly close to Home. Parent/display
zoom never changes envelope precision: generation always uses base zoom 17.

Per-sector evidence includes selected-band `observation_count`,
`occupied_cell_count`, `furthest_cell_id`, `furthest_cell_observation_count`,
and `history_complete`. `qualifying_cell_passage_count` is the sum of stored
**all-band** base-cell passage counters in cells containing selected-band
observations. It is not a count of altitude-specific passages or unique flights;
no per-band passage history can be reconstructed from the existing schema.
The supporting count at a maximum cell concerns that whole cell and window,
not proof of multiple sightings at one exact farthest coordinate.

A lower-band notch diminishing in higher bands is consistent with screening.
Similar band boundaries can indicate shared constraints, but neither pattern
uniquely identifies terrain, terrestrial noise, antenna response or receiver
limits. Traffic distribution differs by altitude, and receiver density/range
share reception limitations. A maximum supported by very few observations is
weaker evidence than a repeatable boundary with substantial support. Compare the
same source, Home and dates; the authoritative range ring may cover a different,
longer historical period than the selected density window.

FAA-derived outputs describe reported traffic extent within the feed/geographic
filter, not reception range. They are available on demand through the status
page/API but do not appear as range-ring comparisons on the FAA map. The FAA
range worker and authoritative range routes remain disabled. Unknown-altitude
reports contribute only to All Traffic; raw assigned altitude is not treated as
measured altitude. Sparse cadence and repeated held-position snapshot credits
remain unchanged. No interpolation or forward prediction credits new cells.

## Storage and operational cost

Window aggregation uses private disk snapshots and temporary SQLite, then
streams base cells into fixed-size sector accumulators. This bounds memory for
large histories. Temporary space must accommodate the SQLite snapshot and
window aggregation database; generation can take time on large datasets.
Serialization and generation release the collector lock after snapshot copying.
Map bbox heat-map requests retain the existing query path; complete GeoJSON
exports retain bounded-memory disk staging. No new third-party package is needed.
