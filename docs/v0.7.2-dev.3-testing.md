# v0.7.2-dev.3 — startup configuration repair

Dev.2 added `trusted_networks` to the Supervisor configuration and runtime validator but omitted it from `settings_defaults.json`. The independent recovery/startup validator rejects unknown fields, so a normal Supervisor options document sent the application into settings recovery before connecting to any feed. Changing the SWIM product or feed credentials could not resolve that mismatch.

Dev.3 synchronizes the recovery defaults with all shipped manifest options. Tests assert exact manifest/default parity, accept a complete SFDPS manifest including trusted networks, migrate older SFDPS options without changing the input source, and verify that those complete options reach the collector through the actual bootstrap validation path. Existing rejection of genuinely unknown fields remains.

The selected `source` remains authoritative: `swim_sfdps` selects SFDPS regardless of the legacy `swim_product` field. Checked settings snapshots now normalize the legacy field to match the selected source. This does not automatically rewrite the Supervisor UI's legacy selector. The recovery page, recovery status and saved settings build metadata now report the current build instead of old hard-coded versions.

Install dev.3 over dev.2, retain your current SFDPS settings, and restart. Expected logs include the persistent settings snapshot message and SFDPS connection/startup messages instead of the collection-paused recovery message. If credentials or source were independently changed/lost, the explicit saved-settings restore remains available; this update does not automatically replace current settings from a backup. Persistent density/range files are not changed by this repair; transient motion/history restarts as usual.

All dev.2 trail/export/model behavior remains; see [dev.2 feature notes](v0.7.2-dev.2-testing.md). A HAOS installation check remains necessary; automated startup tests use synthetic credentials and a mocked collector, not the live FAA service.
