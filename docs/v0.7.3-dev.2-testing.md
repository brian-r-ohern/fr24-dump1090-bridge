# v0.7.3-dev.2 — recording a representative day

1. Install the source package as your local test app. Refresh the repository/settings page before updating, then hard-refresh the map with **Ctrl+Shift+R** after installation. Confirm `/status` reports `0.7.3-dev.2`.
2. Select the intended source as usual. Expand **Map controls → Development recording**. Select **Start 24-hour recording**. This deliberately starts the recording; enabling debug logs is not necessary.
3. After a minute, check that snapshot/sample counts and disk bytes increase. Record the process RAM and estimated one-hour history RAM. Inspect drops and write errors; ideally both remain zero. Preserve the same source for the test day. The source-specific session resumes automatically after a restart until its original deadline.
4. Optional recovery check: restart the app after a few minutes. Reopen the panel and verify the session deadline is unchanged and the earlier observations remain exportable. A source switch uses a separate recording file; it does not mix feeds.
5. After several hours, note disk growth and resource diagnostics. The default 2 GiB disk ceiling and low-space check may end a busy recording early; its status explains why. This is part of measuring feasibility, not a guarantee that every source will fit a full day.
6. At the deadline, the UI changes from recording to saved. The completed day's window is preserved for later download. Select **Export recorded day** for `.geojson.gz`; select **Export replay snapshots** for `.jsonl.gz`. You can stop early and export too. An export while recording is a consistent snapshot; later observations will be included in the next export.
7. Keep both files for analysis. GeoJSON preserves full positioned observation records and breaks lines for gaps/discontinuities. JSONL preserves normalized input batches, including repeated/unpositioned records and field timing metadata, plus minute resource measurements. Raw upstream transport frames are not captured.
8. On a local computer with Python, replay without network connections or real-time delays:

   ```sh
   python tools/replay_recording.py aircraft-recording-SOURCE-DATE.jsonl.gz --events replay-events.jsonl
   ```

   The printed summary counts pattern-label entries, not unique maneuvers. Replay uses the motion model in the source package and does not infer intent. Neither the SQLite archive nor its download is a live restreaming service.

## Assessment

Compare one-hour history RAM estimates after warmup with process RSS, retained sample counts, physical recording bytes, and the final gzip file sizes. Note traffic volume, source cadence, recording losses/errors, restarts, and any source changes. Disk bytes include two compressed representations: raw normalized snapshots for exact replay and distinct positions for GIS export. They are an upper estimate for a future compact history-only store.

## Validation boundaries

Automated unit and actual HTTP-route tests exercise recording, per-source isolation, unsampled inputs, duplicate position handling, restart continuation, original deadline expiry, storage/queue loss reporting, GeoJSON/replay metadata, and trusted-network gates. FAA analytical downloads work while aircraft-feed endpoints remain blocked. The dev.1 popup regression tests are retained.

Validation completed in this environment: **205 Python tests passed**, including nine new recording tests; popup persistence, motion popup, history, source-switch, and recording-control Node checks passed; the map JavaScript passed syntax checking. Chromium is unavailable here, so browser layout/interaction was not verified. The HAOS image build/AppArmor runtime and a full live 24-hour recording still need installation testing. The existing one-hour live history is unchanged; active-aircraft retention beyond an hour and prior-motion highlighting are not part of this experiment.
